01

Seek 为什么慢：追帧的成本模型

视频只能从关键帧开始解码——即不依赖任何其他帧、自身就能独立解码的帧 （H.264 里叫 IDR，H.265 里叫 IRAP）。Seek 到任意时间点 T 时，播放器要先回退到 ≤T 的关键帧，再把中间所有帧解码一遍「追」到 T——这段追帧过程（行话叫 preroll）才是 Seek 耗时的大头。

成本可以粗略写成：seek_latency ≈ 定位/IO + N_preroll × t_decode + 首帧渲染 （N_preroll＝追帧区间要解码的帧数，t_decode＝单帧解码耗时）。 点播场景相邻两个关键帧的间隔（GOP，画面组）普遍 2~10 秒、几十到几百帧，优化只有两个方向：

  • 少解码——把追帧区间里没人依赖的帧直接丢掉，本文主题；
  • 快解码——让解码器远快于播放速度地跑（第 5 章顺带覆盖）。

02

哪些帧可以丢：参考性才是唯一判据

视频压缩靠「帧间预测」：一帧只记录它与某些已解码帧的差异，解码时拿那些帧当底子还原。 被当作底子的就是参考帧，「谁参考谁」连成的依赖链就是参考链； 解码器内部用一小块缓存 DPB（Decoded Picture Buffer，解码图像缓存） 存放还会被引用的帧，不被引用的帧输出即弃。于是丢帧的后果泾渭分明：

  • 丢非参考帧——没有任何帧依赖它， 解码器甚至不知道它存在过，零代价；
  • 丢参考帧——依赖它的帧解码出错， 错误沿参考链逐帧扩散成花屏。

很多资料把「丢非参考帧」等同于「丢 B 帧」，这是错的。I/B/P 和参考性是 两个互相独立的属性：

  • I/B/P 回答「它需要谁」——当前帧怎样参考别人：I 不参考任何帧； P 用一份候选参考帧清单（参考列表）；B 用两份。记录在 slice header 的 slice_type 字段里（slice 是一帧内部的分条，slice header 是每条开头的说明信息）；
  • 参考性回答「以后谁需要它」——当前帧是否会被别人参考：参考帧留在 DPB 给后来的帧当底子；非参考帧输出即释放。写在 NAL 头里。

一个说的是输入，一个说的是输出，互相推导不出来—— 组合出的六种情况在真实码流里都可能存在：

B-pyramid：为什么 B 帧也能成为参考帧。传统 B 帧只参考两侧的 I/P 锚点， 自己是不被引用的「叶子」；B-pyramid 把连续 B 帧组织成层级 （主流编码器 x264/x265——最常用的 H.264/H.265 开源编码器——默认开启）：

  • 先让中间的 B2 参考 I0/P4，并把解码后的 B2 保留在 DPB 里；
  • 再让两侧的 B1/B3 参考 B2——B2 仍是 B 帧（用两个参考列表预测自己）， 却同时成了别的 B 帧的参考；
  • 本文称 I0/P4 为第 0 层（金字塔底部）、B2 为第 1 层（中间参考层）、 B1/B3 为第 2 层（上层叶子）——层号只是讲解编号，不等同于 HEVC 的 TemporalId；
  • 收益：叶子 B 用上距离更近的参考帧，压缩效率更高；代价：部分 B 变成参考帧， 不能再随意丢弃。

03

如何判定：NAL 头 1~2 字节就够了

背景：H.264/H.265 码流由一个个 NAL 单元（统一格式的「数据包裹」）组成， 每个包裹开头 1~2 字节的 NAL 头标明里面装的是什么：

  • VCL NAL（Video Coding Layer）——真正装图像数据的包裹；
  • 非 VCL NAL——SPS/PPS（参数集，记录分辨率等全局参数）、SEI（附加信息）等。

两个标准都把参考性直接写在了 NAL 头里——判定不需要解码，甚至不需要解析 slice header，这正是「解码前丢帧」可行的根本原因：

  • H.264：看 1 字节 NAL 头里的 nal_ref_idc（2 bit）。 == 0 → 非参考帧。标准约束同帧所有 slice 一致，且 IDR/SPS/PPS 必须非 0， 所以读 AU（Access Unit，一帧对应的全部 NAL 的集合）里第一个 VCL NAL 即可判定整帧。
  • H.265：看 2 字节 NAL 头里的 nal_unit_type（6 bit）。 VCL 类型 0~15 成对出现，偶数（_N 后缀）= 非参考。 FFmpeg 的判定函数就是这张表：ff_hevc_nal_is_nonref() （libavcodec/hevc/hevcdec.h:653）。

两个 HEVC 特有细节：
① _N 严格含义是「同一时域子层内非参考」——时域分层是把帧分成若干「帧率层」 （TemporalId 即 tid，就是层号；只解低层得到低帧率版本）。绝大多数点播流只有一个时域层 （tid 恒 0），此时 _N 就是真非参考，FFmpeg 软解也直接丢； 多时域层流严格只保证最高层 _N 安全。
② CRA(21) 是 open-GOP 关键帧，它后面紧跟一批 RASL(8/9) 帧： 显示在 CRA 之前、解码在 CRA 之后，且参考了上一个 GOP 的帧 （跨界借参考帧，省码率）。比如显示顺序 … P29 │ B30 B31 CRA32 … 中，B30/B31 就是 RASL，参考了 P29。连续播放：P29 刚解完还在，B30/B31 正常解； Seek 跳到 CRA32：P29 根本没解码，B30/B31 的参考不存在、解不出来 → 必须丢弃，画面从 CRA32 开始——不丢会花屏，这是正确性要求。

整包判定：~30 行判断一个 AVPacket 能否整包丢弃

/* 返回 1：该 packet 的 VCL 全部非参考，可整包丢弃（AVCC/HVCC 长度前缀格式） */
static int packet_droppable(const uint8_t *data, int size,
                            int is_hevc, int nal_len_size /* 一般为 4 */)
{
    int i = 0;
    while (i + nal_len_size < size) {
        int nal_size = 0;
        for (int j = 0; j < nal_len_size; j++)
            nal_size = (nal_size << 8) | data[i + j];
        const uint8_t *nal = data + i + nal_len_size;
        if (nal_size <= 0 || i + nal_len_size + nal_size > size)
            break;                                  /* 数据异常，保守不丢 */

        if (is_hevc) {
            int type = (nal[0] >> 1) & 0x3F;
            if (type <= 15)                         /* VCL */
                return (type & 1) == 0;             /* _N 偶数 → 可丢 */
        } else {
            int type = nal[0] & 0x1F;
            if (type == 1 || type == 5)             /* VCL */
                return ((nal[0] >> 5) & 0x3) == 0;  /* ref_idc==0 → 可丢 */
        }
        i += nal_len_size + nal_size;               /* SPS/PPS/SEI：跳过继续找 */
    }
    return 0;
}

不想自己写上面那样的 NAL 解析？FFmpeg 在三个阶段已经把「这一帧是什么」的答案算好了， 按付出的成本从低到高：

  • 容器层——读包上的现成标记，零成本：MP4 有个可选的 sdtp box （封装时逐帧记录「是否被别的帧依赖」的元数据表），demuxer 解析后直接在数据包上打 AV_PKT_FLAG_DISPOSABLE 标记（libavformat/mov.c:11806）， 判定只是查一个 bit。缺点：封装工具没写 sdtp 就拿不到， 得退回 NAL 头解析兜底；
  • 解析层——轻量解析，不解码：av_parser_parse2() 是 FFmpeg 的码流解析器，把压缩包喂给它，它只解析各级头部（NAL 头、slice header）、完全不碰像素。 基于 demuxer 吐出的 AVPacket（下面的 pkt）判定帧类型和关键帧， 完整写法： 
    /* ① 是否关键帧：最便宜——demuxer 按容器关键帧索引已打好标记，读 flags 即可 */
int is_key = !!(pkt->flags & AV_PKT_FLAG_KEY);

/* ② 帧类型 I/B/P：把 pkt 过一遍轻量解析器（只读头部，不解码像素）。
      avctx 是按流参数填好的 AVCodecContext，无需打开解码器 */
AVCodecParserContext *parser = av_parser_init(avctx->codec_id);
uint8_t *out; int out_size;                   /* 组帧输出，这里用不到 */
av_parser_parse2(parser, avctx, &out, &out_size,
                 pkt->data, pkt->size, pkt->pts, pkt->dts, -1);

enum AVPictureType type = parser->pict_type;  /* AV_PICTURE_TYPE_I / P / B */
int key_by_parser       = parser->key_frame;  /* 1 = 关键帧（IDR / recovery point SEI） */
    原理见 3.1/3.2：解析器读 slice header 的 slice_type 查表得到帧类型， 见到 IDR 或 recovery point SEI 就置 key_frame； AV_PKT_FLAG_KEY 则来自容器关键帧索引；
  • 解码层——解完才知道，只能事后用：解码输出的每个 AVFrame 自带这两个信息，直接读 frame->pict_type（I/P/B）和 frame->flags & AV_FRAME_FLAG_KEY（非 0＝关键帧）。 此时解码成本已经花掉，这条路只能服务「解码后丢帧」（比如作用点④的不渲染判定）， 省不了解码本身。

硬解落地：为什么 iOS 顺手、Android 要自己动手

FFmpeg 接入硬解有两种模型，skip_frame 行为截然不同：

  • hwaccel 模型（硬件加速——FFmpeg 照常拆包、解析 NAL，只把像素级计算交给硬件； 如 iOS VideoToolbox、VAAPI、NVDEC）：丢弃决策在软件层完成，被丢的 NAL 根本不会提交给硬件，skip_frame ✅ 生效；
  • wrapper 模型（包装——FFmpeg 只当搬运工，把整包数据原样转交系统解码器； 如 Android MediaCodec）：整包透传给系统黑盒，skip_frame ❌ 完全无效—— 丢帧必须发生在喂入之前。

PITFALL 01
「丢 B 帧」≠「丢非参考帧」

x264/x265 默认开 b-pyramid，参考 B 约占 B 帧一半；按 pict_type 丢帧必花屏。 必须按 NAL 头判参考性（H.264 nal_ref_idc、H.265 _N 类型）。
PITFALL 02
HEVC open-GOP：CRA + RASL
点击翻面 ↻
open-GOP 里 CRA(21) 后面跟着一批 RASL 帧（8/9）：显示在 CRA 之前、 参考上一个 GOP 的帧。连续播放没问题；Seek 跳到 CRA 时上一个 GOP 没解码， RASL 的参考不存在、解不出来，必须丢弃——不丢会花屏。闭 GOP（IDR）流无此问题。
PITFALL 03
HEVC 时域分层的 _N 语义
点击翻面 ↻
_N 严格含义是「同子层非参考」；单时域层流（绝大多数点播）可无脑丢， 多时域层流只保证最高 TemporalId 层的 _N 绝对安全。
PITFALL 04

点击翻面 ↻
AV_PKT_FLAG_DISPOSABLE 来自 MP4 的 sdtp box， 封装器不写就没有；判定逻辑要有 NAL 头解析兜底。
PITFALL 05
MediaCodec 上 skip_frame 无效
点击翻面 ↻
wrapper 模型不拆 NAL，FFmpeg 的 skip_frame 设了也白设； 丢帧必须发生在 queueInputBuffer 之前。

总结与源码索引

Q1 · 丢非参考帧，解码器支持吗？

  • FFmpeg 软解 / hwaccel 模型：原生支持—— skip_frame = AVDISCARD_NONREF，丢弃发生在 NAL 解析层，硬件无感；
  • MediaCodec 这类 wrapper：不支持——但也不需要：非参考帧的定义保证了 「喂入前丢包」与「解码器内跳过」效果完全等价，判定只需读 NAL 头 1~2 字节；
  • 解码前丢不掉的参考帧：用「解码不输出」（DECODE_ONLY / DoNotOutputFrame）和「输出不渲染」（releaseOutputBuffer(false)） 两层兜底快速追帧。

Q2 · 参考帧与 I/B/P 的关系？

  • 互相独立的两个属性：slice_type 决定 I/B/P（怎么预测自己）， NAL 头决定参考性（是否被引用）；
  • 判定：H.264 看 nal_ref_idc == 0，H.265 看 VCL 类型的 _N 后缀（偶数）；
  • B 帧可以是参考帧（b-pyramid），P/I 也可以是非参考帧—— 安全丢帧的唯一判据是参考性，不是帧类型。
